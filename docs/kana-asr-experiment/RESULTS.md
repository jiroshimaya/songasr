# 洋楽歌詞のカナASR、改良できるか試してみた

## 背景

以前、[「洋楽の音声からカタカナ書き起こしを作る」](https://qiita.com/shimajiroxyz/items/37c1e8d309403165e33c)という記事で、次のようなパイプラインを試した。

1. `facebook/wav2vec2-lv-60-espeak-cv-ft` で音声→IPA音素列を認識
2. `ipapy` でIPA→ARPABET相当の記号に変換
3. `arpakana` でARPABET→カタカナに変換

このとき課題として挙げていたのが「全体的にはまだ正解と比べて聞き逃しが多い」「音素ASRのノイズ耐性不足」だった。今回はこのボトルネックを解消できないか、手持ちの検討用リポジトリ (jiroshimaya/songasr, jiroshimaya/kanasim, jiroshimaya/e2k-asr-eval) の資産を使って再検証した。

## 試した改良アプローチ

### アイデア: 日本語ASRモデルに英語音声をそのまま食わせる

前回のパイプラインは「IPA音素認識 → 記号変換 → カタカナ変換」と3段階を踏んでおり、各段階で情報が失われる。一方で「空耳」という現象そのものは、日本語の音韻システムで英語の音を無理やり解釈した結果起きている。

だったら、最初から**日本語のカナを出力するように学習されたASRモデルに英語音声を直接入力すればいいのでは**、というのが今回の仮説。songasr リポジトリ (`scripts/run_kana_asr.py`, `scripts/run_kana_whisper_asr.py`) で実際に2通り試されていたので、それぞれ再現・検証した。

#### 案A: Whisperを日本語モードに固定し、カナ以外のトークンを禁止する

OpenAI Whisperに `language="ja", task="transcribe"` を強制し、さらに `suppress_tokens` でカタカナ・ひらがな・句読点以外のトークンを丸ごと生成禁止にする(`scripts/download_whisper_tokens.py` と同じロジックで `multilingual.tiktoken` から対象トークンIDを抽出)。理屈の上ではWhisperの日本語デコーダーに英語音声を「日本語として」解釈させられるはず、という発想。

**結果: 使い物にならなかった。** small/base/tinyいずれのモデルでも、英語音声の音響的な特徴とは無関係な、文法的に破綻のない日本語の文章を「創作」してしまう(ハルシネーション)。

```
入力: "Under the moon and the quiet sky so clear" (TTS音声)

whisper small (beam_size=5):
「このビデオを見て、どっちがこれをしたのかは見すので、かわいないことだけだよ
またいきたいマンゴーラン...ただらかあつままんこのビデオをチャンスかなとは
もないそんなことなんやしてもだがどうやわ」

whisper tiny/base (greedy):
「このように、このように、このように、...」(同じフレーズの無限ループ)
```

原因は構造的なもの。Whisperは自己回帰(前の出力トークンを見て次を予測する)デコーダーで、強い言語モデル的な事前分布を持っている。`suppress_tokens` でカタカナ・ひらがな以外を禁止しても、「それらしい日本語の文」を生成する圧力自体は残るため、音響特徴よりも学習した日本語の文脈的な尤もらしさを優先してしまう。カタカナ縛りにした結果、支離滅裂な内容ではなく**流暢だが原音と無関係な日本語**が出てくる、というのが今回わかった一番意外な点だった。

→ この案は今回のユースケースには不向きと判断し、定量評価からは除外した。

#### 案B: 日本語カナ認識用wav2vec2モデルに直接入力する

`AndrewMcDowell/wav2vec2-xls-r-1b-japanese-hiragana-katakana` (ひらがな・カタカナを出力するよう学習されたCTCベースのwav2vec2) に英語音声をそのまま入力し、出力を `pyopenjtalk.g2p(text, kana=True)` でカタカナのみに正規化する(songasrの `run_kana_asr.py` の `text_to_katakana` と同じ)。

CTCはWhisperと違って**1フレームごとに何らかのラベルを出す非自己回帰モデル**なので、「文章としての尤もらしさ」を優先して創作することができない。この構造の違いにより、ハルシネーションは起きなかった。

## 実験方法

- 前回記事と同じ例文 `"Under the moon and the quiet sky so clear"` に加え、縮約形・子音クラスタ・機能語など歌詞によくあるパターンを含む文を4つ追加し、計5文で検証。
- 各文を [gTTS](https://pypi.org/project/gTTS/) で音声合成(ffmpegなしで完結させるため、mp3を`soundfile`で直接デコードして16kHzモノラルに変換)。
- 各文について、素直な英単語→カタカナ変換(「アンダー・ザ・ムーン」のような、外来語表記としてごく標準的なカナ化)を人手でリファレンスとして用意。
- 得られたカナを、jiroshimaya/kanasim(Soramimicの本番アプリでも使われている音韻距離計算ライブラリ)でリファレンスとの距離を算出し、数値化して比較。距離が小さいほどリファレンスに近い。

検証コードは本ディレクトリ (`docs/kana-asr-experiment/`) にまとめている。音声ファイル(TTS/歌唱音源とも)は再生成可能なため含めておらず、`gen_audio.py` / `run_experiment.py` / `run_song_experiment.py` を実行すると同じ手順で再現できる。

## 考察

正直に書くと、**「リファレンスの外来語カナ表記にどれだけ近いか」という指標では、旧手法(IPA→ARPABET→arpakana)の方が一貫して優れていた。** 5文すべてでwav2vec2-jaの距離が旧手法を上回り(悪化し)、平均でも約1.7倍の差がついた。「日本語ASRモデルに直接food入力すれば良くなるはず」という当初の仮説は、少なくともこの評価方法の上では外れた。

ただしこれは指標の性質を踏まえて解釈する必要がある。

- 旧手法(baseline)は「英語音素をCMU発音辞典的なARPABETに変換し、決め打ちのテーブルで機械的にカナ化する」パイプラインで、これは実質的に**標準的な外来語カナ表記のルールをそのまま実装したもの**に近い。だから「標準的な外来語カナ表記」をリファレンスにした評価と相性が良いのは、ある意味当然の結果ともいえる。
- 一方wav2vec2-jaは「日本語の音韻・アクセント体系を学習した音響モデルが、英語の音をどう聞き取るか」を直接表現したもので、これはむしろ**本物の「空耳」が起きるメカニズムに近い**。s1の出力 `アンジョダムウネンダコワエツカイソークエル` は "so" の部分が `ソー` とほぼ完全一致するなど、部分的には人間の空耳的な聞き間違いに近い質感がある。標準カナ表記との距離が大きいのは「不正確」なのではなく「素直な変換とは違う聞こえ方をしている」だけの可能性がある。
- 今回のリファレンスは筆者が手で作った「素直な外来語読み」であり、実際の空耳(=日本語話者が英語をどう聞き間違えるか)の正解データではない。空耳生成用途で本当に評価すべきは「外来語表記との距離」ではなく「日本語話者が実際にそう聞こえるかどうか」であり、この2つは似て非なるものだった、というのが今回一番の学びだった。

Whisper案(案A)は、案の設計自体はsongasrリポジトリで既に試みられていたアイデアだったが、自己回帰デコーダー特有のハルシネーションで実用にならないことを確認できた。これは「大きい・賢いモデルほど良い」とは限らない好例で、CTCのような非自己回帰モデルの方がこの用途(音響への忠実性が最優先)には向いているという傍証になった。

## 実際の歌唱音源での検証

上記はすべてgTTSの読み上げ音声だったので、「本物の歌声でも同じ傾向になるか」を追加で検証した。音源は[前回とは別のQiita記事](https://qiita.com/shimajiroxyz/items/7e43427134330faa6731)で使ったのと同じPixabayのロイヤリティフリー楽曲([該当URL](https://cdn.pixabay.com/download/audio/2025/03/22/audio_f46c5fa5ad.mp3)、jiroshimaya/songasr の `scripts/download_sample_song.py` が参照しているのも同じ音源)。この曲、そもそも前回記事の例文 `"Under the moon and the quiet sky so clear"` の出どころだったらしく、実際に歌詞として歌われていた。

### 手順

1. 音源をダウンロードし、librosa+soundfileで16kHzモノラルWAVに変換(ffmpeg不使用)。
2. openai-whisper (small, 英語モード, `word_timestamps=True`) で歌詞の書き起こし+タイムスタンプを取得。これは英語→英語の素直な書き起こしタスクなので、案Aで問題になった「日本語に強制した時のハルシネーション」とは無関係。実際、書き起こされた歌詞は文法的にも一貫しており、フレーズ単位の区間長(4〜8秒程度)も不自然な値はなく、ループ的な繰り返しも見られなかった。
3. 書き起こし結果から代表的な5フレーズを選び、区間の前後に0.2〜0.3秒のパディングを加えて音声を切り出し(songasrの`split_audio_by_segments.py`と同様、次のセグメント開始時刻を超えないようにする考え方を踏襲)。
4. 各区間についてbaseline / wav2vec2-jaを実行し、TTS実験と同じ要領で手書きリファレンスとのkanasim距離を算出。

### 結果

| # | 歌詞 | baseline | 距離 | wav2vec2-ja | 距離 |
|---|---|---|---|---|---|
| song1 | Under the moon and the quiet sky so clear | アンダーダムーアンダクワイイッツカイソウクリー | 43.6 | アンデーダエデコワツカアイソークイ | 96.3 |
| song2 | A whisper of hope is all I hold near | アウィスパーラヴハウイサライホウダニー | 83.9 | アオイシプガワオエショーダイホーネゲエ | 143.1 |
| song3 | Every breath, every word | エヴリーブレイエヴリーバード | 22.5 | エーヴイープーエーヴイーボン | 58.9 |
| song4 | Hands raised high with the hearts in tears | ハンズレイズドハイウィダシンシー | 55.8 | エーズヴェイーカーウトハーセチ | 113.1 |
| song5 | Oh eternal light, that shines so pure | ス | 121.4 | カオイヤシャーヤソヒウ | 111.6 |
| | **平均** | | **65.4** | | **104.6** |

TTS実験の平均(baseline 52.9 / wav2vec2-ja 91.2)と比べると、**両手法とも実際の歌声では距離が悪化した**(baseline: 52.9→65.4、約1.24倍。wav2vec2-ja: 91.2→104.6、約1.15倍)。歌声はTTSの読み上げよりも難しい、という前回記事の課題認識(ノイズ耐性・頑健性の話)と整合する結果になった。

前回記事の例文とまったく同じ歌詞であるsong1(実際の歌声)とs1_moon(TTS)を直接見比べると、baselineは43.6→(TTS)45.5とほぼ横ばいだった一方、wav2vec2-jaは79.3→96.3とはっきり悪化しており、**wav2vec2-jaの方がメロディ・ピッチの影響を受けやすい**傾向がうかがえた。CTCモデルはフレーム単位で判定するため、歌唱で音を伸ばす(メリスマ・ビブラート)と同じ音素が続いているのか新しい音素に移ったのかの境界判定が難しくなり、認識がより崩れやすいのではないかと考えられる。

その傾向が最も極端に出たのが**song5**で、baselineの出力がなんと`ス`の1文字だけになった。原文 "Oh eternal light, that shines so pure" に対してほぼ全ての音素認識が抜け落ちている。他の4区間ではそこまで極端な脱落は起きていないため、この曲のこの箇所特有(長く伸ばす音や高い音程など)の要因の可能性が高く、5区間だけでは一般化はできない。ただし「歌唱音声では極端な聞き漏らしが起こりうる」という前回記事の懸念を、具体例として再現できたことは収穫だった。

全体として、**「baselineがwav2vec2-jaよりリファレンスに近い」という順位はTTSでも歌唱でも変わらなかった**。歌声になったことで新たに生まれた問題というより、TTSで見えていた課題(認識精度・頑健性)が歌声でさらに増幅された、というのが実態に近い。ただし今回はワンショット・1曲・5区間のみの検証であり、曲調(テンポ、メロディの跳躍度、伴奏の有無)によって結果が変わる可能性は高く、この結論はまだ暫定的なものと捉えるべき。

## 今後の課題

- **リファレンスの質**: 手作りの「標準外来語カナ」ではなく、実際の空耳(替え歌・空耳歌詞)や、jiroshimaya/e2k-asr-eval で使われているBEP辞書(英単語→カタカナ読みの対応辞書)のような、単語レベルでより実態に即したデータでの評価に切り替えたい。
- **歌声のサンプル数を増やす**: 今回は1曲・5区間のみ。曲調の異なる複数の楽曲・より多くの区間で検証しないと、「歌唱で悪化する」という傾向が一般的なものかは判断できない。特にsong1で見られた極端な聞き漏らしは他の曲でも再現するか要確認。
- **ノイズ耐性**: 前回記事の課題だった「背景雑音への耐性」(BGM込みの音声)は今回のPixabay音源でも一部含まれるはずだが、明示的な検証はできていない。ボーカル/伴奏の分離有無での比較が必要。
- **wav2vec2-jaの改善余地**: 今回はモデル出力をそのままpyopenjtalkでカナ化しただけ。信頼度(logits)を使った複数候補の中からリファレンスに近いものを選ぶ、あるいはCTCのビームサーチ幅を広げるなど、まだチューニングの余地がある。
- **単語単位での評価**: 文単位ではなく、jiroshimaya/e2k-asr-eval的に英単語1つずつをTTSして評価すれば、どの音素・どの単語パターンで各手法が強い/弱いかがより明確になるはず。
